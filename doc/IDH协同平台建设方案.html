一页结论

先看这五条，其余都是展开

1. 这是对账项目，不是监控项目。把原厂的"发货账"、IDH 的"消耗账"、仓库的"实盘账"用同一套料号、批次和事件标准对齐。三账一旦能自动对上，生产进度和消耗透明度是副产品。

2. 建设顺序不可颠倒：主数据（料号 + 批次编码）→ 事件（收发货、领用、报工）→ 对账（差异分类 + 锁账）→ AI（归因 + 预测）。顺序反了，AI 只是在分析垃圾数据。

3. 上线前必须做一次全量期初盘点定基。否则历史差异会永久污染三账，系统从第一天起就"不准"，随后失去所有人信任。

4. 推行靠合同条款 + IDH 收益，不靠行政命令。把"数据同步义务"写进工单合同，把"平台记录"设为结算唯一依据；同时让 IDH 拿到自动对账、结算加速、VMI 降资金占用。IDH 配合的动力必须大于隐瞒的收益。

5. AI 从两件事切入：单据结构化（PDF 工单/送货单自动入系统）与差异归因（差异明细自动给出 Top3 原因和核查清单）。这两个场景低风险、可验证、立刻省人力。

01 · 问题拆解：断裂不在"没系统"，而在"没有共同基准"

你描述的两个症状——原厂不清楚 IDH 生产情况、IDH 不清楚订单消耗情况——本质是同一个问题的两侧：双方各自维护一本账，且两本账没有共同的锚点。再加一本"仓库实盘账"，三本账之间没有任何自动勾稽关系，只能靠月末人工拼表。

1.1 信息断点分布

业务环节原厂能看到的IDH 能看到的双方都看不到的（真正的黑洞）
需求与配额客户订单、内部预测、给 IDH 的额度只有已下达的那张工单额度已用 / 剩余、后续 8 周需求趋势
发货与在途发货单、物流单号、发票只看到"货到了"分批到货计划、在途实时状态、异常滞留
芯片库存账面已售 / 寄售数量自己仓库的实物两本账的差额、批次账龄、呆滞判定
投产与在制基本为零（靠问）自己产线的实际状况工序级进度、良率、报废、返工
成品出货只看到最终出货结果自己的出货记录出货数量与芯片消耗量的对应关系（单耗）
结算发票金额、付款计划自己的应收消耗口径、差异责任归属、该扣该补

1.2 为什么"Excel + 微信群"必然失效

失效原因具体表现
时点不一致微信里的进度是"昨天下午"的状态，发货单是"上周"的，库存表是"前天"导出的。三个时间轴拼不出一个可用于决策的数。
口径不一致"已投产 5000"——是领料 5000、贴片 5000、还是测试完成 5000？同一个词在两边指不同的事，对账时必然打架。
缺批次锚点只记数量不记批次。一旦出现批量性失效，无法从成品 SN 反查到晶圆批，质量责任无法界定，只能整批扣款。
不可审计聊天记录和邮件不能作为结算依据。争议一旦发生，回到"各说各话"，最终由强势方拍板，弱势方下次更不愿报实数。
自检：命中 3 项以上，说明必须上平台了
  • 月度对账耗时超过 5 个工作日
  • 账实差异率长期高于 0.5%，且说不清原因
  • 需要专人每周向 IDH 催进度、催库存表
  • 同一个批次的良率，两边报出两个版本
  • 呆滞料责任无法界定，最终原厂兜底
  • 客户急单时，无法在 1 小时内回答"IDH 手上还有多少可动用、几天能出货"

02 · 五条设计原则

原则含义不遵守的后果
一个料号、一个批次、一个基准单位全平台料号唯一；批次贯穿晶圆批→封装批→成品 SN；计量统一以"颗"为基准，盘/箱只做容器换算。编码不统一，三账永远对不上，且差异无法归因。这是最容易低估、代价最高的一项。
事件驱动、只追加、不可篡改每一次收发货、领用、报工都生成一条带时间戳与操作人的事件；账是由事件累加算出来的，不是人工改出来的。账可以被改，就等于没有账。审计时无法自证。
双向透明，不是单向监控原厂看得见 IDH 的在制与库存；IDH 同样看得见原厂的订单池、配额余额、在途批次、结算进度。做成监控工具，IDH 一定用"填假数"来对抗，平台数据半年内失去价值。
最小采集只采对账和交期承诺必需的节点（收货、领用、关键工序完工、入库、出货），不追求全工序 MES 级覆盖。IDH 双录负担过重 → 抵触 → 数据延迟或造假。第一期死在"要求太多"。
AI 只做辅助，结论必须可溯源任何 AI 输出的结论都要能点回原始单据或事件；不做自动扣款、自动判定责任。一次错误的自动判定，会让双方都不再信任系统。

3.1 三本账的更新时点

账本公式更新时点 / 由谁驱动
A 原厂账
发货视角		A = 期初 + 发货 − 退货 − 转售 − 已确认消耗发货单生效、退货入库、对账确认时更新。由原厂 ERP + 平台共同驱动。
B IDH 账
消耗视角		B = 期初 + 收货 − 领用 − 报废 + 退料每次扫码动作实时更新。由 IDH 现场作业（PDA / H5）驱动。
C 实盘
物理视角		C = 盘点实盘数月度全盘 + 周度循环盘点（按高价值/高流动料号轮盘）。
关键设计：A 与 B 的"消耗"必须是同一个数

最常见的设计错误，是让原厂账按"发票"扣减、让 IDH 账按"领料"扣减。两者永远差一个时间差，差异率恒大于零。正确做法是：统一以"领用事件"作为消耗确认口径，发票只做金额结算，不参与数量勾稽。数量账与金额账必须分开建模。

4.1 十个核心模块的职责边界

模块做什么关键设计点
主数据料号、封装、批次规则、供应商（IDH）、仓库、单位换算、标准损耗率与 ERP 单向同步为源，平台只读；编码规则变更需审批留痕
合同与工单原厂下工单（数量/料号/交期/工艺版本/结算方式），IDH 接单、交期回复、变更（ECO）工单是"数量承诺 + 时间承诺"的载体，必须支持分批交付与变更版本
发运与收货装箱单、批次明细、物流单号、到货签收、差异（短装/破损）登记按"箱/盘/批次"三级扫码，收货即绑定批次
库存与批次账料件库存、寄售库存（原厂所有）、在途、冻结、呆滞账龄库存不是"一个数"，是"按批次 + 状态 + 归属方"的多维台账
生产与报工工单投产、关键工序报工（贴片/测试/老化/包装）、良率、报废、返工只采 4–5 个关键节点，不做全工序管控
成品与出货成品入库、SN 绑定、出货单、与芯片消耗的单耗核对单耗（每台成品消耗几颗芯片）是识别异常的黄金指标
对账中心自动生成对账单、差异明细、IDH 申辩、差异分类、调整单、锁账差异必须挂"原因码 + 责任方 + 处理动作"，不允许自由文本了事
预警库存低于安全线、消耗速率异常、批次账龄超期、交期延误、差异超容差分级推送（企微/邮件），并强制"谁处理、几时关闭"
看板原厂视角：全局库存与在制；IDH 视角：自己的订单、库存、待办同一套指标，两个视角，避免两套口径
AI 助手单据结构化、差异归因、自然语言问数、合同条款抽取、需求预测输出必须可溯源到单据/事件；不参与自动判责
协同沟通台工单级群聊、差异申辩对话、预警处理线程；消息结构化存储并自动标记（承诺/数量/问题/决议），与事件流联动可审计消息不可篡改，绑定工单/差异/预警上下文；AI 自动打标签；聊天记录作为结算证据链的一部分

05 · 核心数据模型

数据模型的成败取决于五个"唯一性约束"。这五条不立起来，后面所有功能都是沙上建塔。

约束规则为什么必须
material_code 全局唯一原厂物料码为唯一主键，IDH 自有料号作为别名映射否则同一颗芯片在两个系统里是两个东西
lot_no 全局唯一晶圆批 + 封装批 + DateCode 组合，不允许 IDH 自行编号批次是质量追溯与责任界定的唯一锚点
container_id 唯一箱 / 盘 / 袋三级容器码，父子关系固定，拆并不改历史数量差异 90% 来自"盘→颗"换算与拆包未登记
event_id 唯一且只追加每条业务事件不可修改，更正靠反向事件冲销保证账可审计、可回溯到人
(wo_id, line_no) 唯一工单行项目粒度，支持分批交付与部分收货一张工单 5 批发货是常态，不能按整单记账

建模技巧：把"数量"拆成四个字段，而不是一个

qty_ordered / qty_shipped / qty_received / qty_consumed。很多系统只存一个"已完成数量"，导致无法区分"发了没收""收了没投""投了没报"，差异出现时只能靠猜。四个字段分开存，差异自动落到具体环节。

06 · 六个关键机制

6.1 编码规则：整个项目最容易翻车的地方

绝大多数"三账对不上"的项目，根因不是软件功能不够，而是编码没统一就开始上系统。建议在开发启动前，先花两周把编码规则定死并公告，写进合同附件。

对象规则示例
料号厂商(3)-品类(3)-型号-封装-版本(2)BMX-SOC-BM1684X-BGA-01
批次号晶圆批-封装批-DateCode，由原厂统一发放，IDH 不得自编L2604-A17-2603
容器码CT-单号-序号，托盘 > 箱 > 盘 三级父子关系，拆并留痕CT-DN20261103-007
成品 SN型号-DateCode-流水，与所用芯片批次绑定BM1684X-2603-000123
基准单位数量一律以"颗"存储；盘/箱仅作容器换算，换算率写入主数据1 盘 = 250 颗（示例）
必须坚持的一条

批次号只能由原厂发放，IDH 侧不允许新建批次。一旦允许 IDH 自编批次，同一批货会出现两个批号，追溯链当场断裂，质量索赔时双方各拿一套证据。

6.2 工单状态机

工单是"数量承诺 + 时间承诺"的载体。状态机的作用是让"生产到哪一步"变成结构化字段，而不是靠人描述。

状态进入条件责任方对三账的影响超时规则
草稿原厂创建，未下达原厂无7 天未下达自动归档
已下达原厂确认下达并生成合同原厂无（仅承诺）IDH 48h 未接单提醒
已接单IDH 确认数量与交期（可提反建议）IDH无—
备料完成所需批次已锁定 / 已到货IDH库存转"已分配"距交期 7 天未备齐预警
投产首次领料IDHB 账扣减（消耗确认）领料后 3 天无报工预警
部分完工首批成品入库IDH成品库存增加—
全部完工累计入库 = 工单数量IDH单耗核算触发单耗偏差 > 3% 触发核查
已出货出货单确认IDH成品库存减少—
已对账期间对账确认双方A 账"已确认消耗"更新—
已关闭差异清零或已开调整单双方锁定，不再变动—
暂停 / 变更 / 取消旁支状态，需附原因码与审批发起方释放已分配库存变更需生成新版本号

6.3 三账重算与差异自动归因

采用双轨计算：事件到达时增量更新（秒级，供看板用），每日凌晨全量重算（供对账用）。两者结果不一致即报警，防止增量逻辑漏算。

差异不直接抛给人，先用规则引擎做一轮自动归因，命中率通常在 70%–85%：

判定条件归因建议动作
A − B 为负，且存在已发货未收货的 DND01 在途未达查物流；超过 ETA 3 天自动升级
A − B 恰好等于在途量D01 在途未达同上，属正常时点差
B 有收货记录但 A 无对应 DN数据错录 / 重复收货核对单据号，做反向事件冲销
B 的领用量 > A 的已确认消耗量D03 领用未报工催 IDH 补报工，锁定工单
C < B 且差额接近该料号标准损耗D04 报废未申报要求补报废单，超容差部分扣款
差异为盘/箱装数的整数倍D06 单位换算核对容器码与换算率
同一批次出现在两个工单的领料记录D05 批次串用追查实物，登记串批调整

6.4 对账节奏：日核对、周清理、月锁账

T+1 自动核对→差异清单推送→IDH 48h 内申辩→周会定责→调整单双签→月结 T+3 锁账→开票 / 付款
环节频率输出硬规则
自动核对每日 02:00差异明细（按料号/批次/原因码）差异率 > 0.3% 当日推送双方负责人
申辩收到后 48 小时内申辩理由 + 附件（照片/单据）逾期未申辩视为认可
定责会每周一次，30 分钟差异责任方 + 处理动作只处理 Top 20 差异，长尾走规则自动核销
调整单随时调整前后数量、原因码、双签记录禁止直接改数，只能开调整单
锁账每月 T+3锁账对账单（PDF，双方电子签）锁账后调整进入下期，不改历史
盘点月末全盘 + 周度循环盘盘点报告 + 差异分析高价值/高流动料号每周轮盘

6.5 多租户与数据可见性矩阵

这是让 IDH 愿意上平台的前提：它必须确信自己的数据不会被竞争对手看到，同时能看到原厂对自己的承诺。

数据对象原厂该 IDH其他 IDH
工单与交期全量全量不可见
库存（含批次、账龄）全量全量不可见
在制与良率全量全量仅匿名行业基准
价格与结算条款全量仅本家条款不可见
终端客户信息全量脱敏（仅型号与数量）不可见
原厂订单池 / 配额余额全量仅本家配额与后续预测不可见
产能占用（全局）全量仅本家不可见

技术上用 PostgreSQL 行级安全（RLS）+ 租户 ID 强制过滤，而不是在应用层写 where idh_id=?——应用层过滤漏一处就是数据泄露。

6.6 数据质量校验规则（部分示例）

  1. 收货数量 ≤ 该 DN 的发货数量，超出拦截并生成差异单。
  2. 领用数量 ≤ 该批次当前可用库存，超出禁止过账。
  3. 累计领用 ≤ 工单数量 ×（1 + 标准损耗率），超出需审批。
  4. 成品入库数 × 单耗 与 领用数偏差 > 3% 触发核查（识别虚报或掉料）。
  5. 同一 DN 重复收货拦截（幂等键 = DN + 箱码）。
  6. 时间序校验：收货 ≥ 发货，报工 ≥ 收货，出货 ≥ 入库。
  7. 批次账龄 > 180 天自动标记呆滞，进入责任判定流程。
  8. 单位换算必须整除校验，非整除需人工确认并留痕。

6.7 · 协同沟通台（CollabChat）：结构化群聊，替代微信群

为什么必须做——微信群是当前最大的信息黑洞

文档 1.2 已将"微信+Excel"列为三账断裂的核心原因。聊天记录散落、口径不一致、不可审计、无法作为结算证据——这些问题不解决，即使系统建好了，运营层面的信息断裂依然存在。CollabChat 将沟通从"群聊"升级为"可审计的业务记录"，嵌入每一个业务上下文。

6.7.1 三种对话模式

不是建一个"大群"，而是在每个业务场景中按需启动上下文对话：

模式触发条件参与者上下文与规则
A · 工单对话工单状态变更时自动激活原厂计划员 + IDH 生产负责人工单号、状态、四数量字段实时可见；系统事件（状态变更、报工）自动推入为系统消息；支持文件/图片上传
B · 差异申辩日核对生成差异明细时自动创建原厂对账 + IDH 仓库/财务差异卡片（料号、差额、原因码、建议动作）上下文绑定；48h 申辩窗口倒计时；逾期未申辩视为认可
C · 预警处理线程预警被触发时创建平台自动推关联人预警卡片 + 关联工单/库存数据上下文；关闭预警必须附处理摘要（文本即归档为消息）；形成完整处理闭环

6.7.2 消息结构化存储与标签体系

聊天不只是一段文字。每条消息存储时就带上下文锚点，AI 在后台自动打标签——人也可以在发送时手动标记：

标签类型含义示例后续动作
commitment交期承诺"下周二能出 3000"与工单交期字段对比，追踪承诺兑现率
number数量提报"目前库存还有 5000 颗"与系统库存数/N 账对照，偏差触发核查
issue问题上报"有一批料好像有问题，良率偏低"关联批次，触发质量追溯建议
reason原因说明"因为设备故障停了半天"与报工缺口时间窗口对照，纳入差异归因上下文
decision决议记录"同意这批先走，后面补单"自动关联调整单，作为审批附件
mention提及@某人生成待办推送，追踪响应时延
关键设计：消息不可篡改，与事件流同等对待

消息表和 event_log 共享同样的"只追加、不可改"原则。发送后不可编辑删除，更正只能追加修正消息。这意味着聊天记录可以作为审计证据链——结合事件流（领料、报工、出货），形成完整的"谁说了什么 + 系统记录了什么"对照时间线。

6.7.3 消息与系统事件的对照关系

聊天里的承诺和数字，必须能和系统事件互相校验。这是 CollabChat 区别于普通 IM 的核心设计：

聊天里说的对应系统事件校验逻辑不匹配时的动作

与差异归因引擎的联动

当差异引擎（6.3 节）遇到未命中规则的差异时，除了检索历史案例库，还会检索该工单/料号的对话记录中带 issue/reason/decision 标签的消息，作为补充线索提供给 AI 归因模型。这使得"聊天中透露但未正式申报"的信息也能被纳入差异分析的上下文。

6.7.4 可见性规则

完全遵循 6.5 多租户数据可见性矩阵——IDH 只能看到自己参与的对话，看不到其他 IDH 的沟通内容。技术上同样用 PostgreSQL RLS + 租户 ID 强制过滤。

工单对话✅✅❌
差异申辩✅✅❌
预警处理线程✅✅❌
自由群聊（按需）✅✅（仅同群成员）❌

6.7.5 AI 智能分析

消息结构化存储后，AI 在三个维度产生价值（详见 08 · AI 能力设计补充）：

  1. 承诺兑现追踪：自动提取聊天中的交期承诺（标签 commitment），与工单实际交付日期对比，生成"承诺兑现率"指标和"频繁承诺失信"预警。
  2. 信息断点检测：当聊天中出现数量/问题相关描述但系统无对应事件时，AI 主动推送提醒"聊天中提到了 X，但系统中未记录对应事件，请确认是否需要补录"。
  3. 争议回溯：对账争议发生时，一键拉出该工单/差异的完整对话时间线 + 系统事件对照线，取代"翻聊天记录找证据"的人工操作。

7.1 与 IDH 现有系统的三种对接模式

C · H5/PDA 直接作业无系统的 IDH扫码即录入，数据质量最高需提供扫码设备与现场培训
务实做法：先 B，再 C，最后 A

首期全部走 B（Excel + 强校验），让业务先跑起来、让双方先尝到对账自动化甜头；第二期给重点 IDH 上 C（扫码）；第三期再对头部 IDH 做 A。反过来先做 API 对接，项目会在接口联调上耗掉半年，业务方早已失去耐心。

7.2 容量与性能

以 10 家 IDH、月均 200 张工单、500 批发货、约 2 万次扫码事件估算，年事件量在百万级，单台 PG 完全够用。真正的瓶颈是月末对账的聚合查询与扫码高峰的并发写入，前者用分析库分流，后者用消息队列削峰即可。

08 · AI 能力设计：先做"省人力"，再做"给判断"

AI 在这个场景里不是噱头，但顺序必须对。先用 AI 解决"录入太慢、差异看不懂"这两个高频痛点，让它天天被用；等数据积累 3–6 个月，再上预测类能力。

8.1 差异归因的具体做法（P0 场景拆解）

不要一上来就让大模型"看一堆数据自己找原因"，那会得到一堆正确但无用的话。正确做法是规则先算、模型后解释：

  1. 规则层用 6.3 节的判定表做硬匹配，能命中 70%–85% 的差异，直接给结论码。
  2. 检索层对未命中的差异，从历史案例库召回 3–5 个相似案例（同料号、同 IDH、同原因码、金额相近）。
  3. 生成层让模型基于"差异数字 + 事件时序 + 相似案例"输出归因假设与核查动作，每条假设必须引用具体事件 ID 或单据号。
PROMPT 骨架 · 差异归因（示例）
系统：你是芯片供应链对账分析师。只能基于给定数据推理，不得编造。
每条结论必须标注依据的事件 ID；无法确定时输出"证据不足"。

输入：
- 差异：料号 BM1684X，期间 2026-10，A=1800，B=1820，C=1790
- 事件流：DN-10021（发货 5000，10-03）… ISSUE-3087（领用 1200，10-21）…
- 报工：WO-2211 于 10-22 报工 1180，scrap=12
- 历史相似案例：3 条（含处理动作与最终责任判定）

输出格式：
1) 差异分解（系统差异 / 实物差异）
2) 归因假设（按可能性排序，每条附依据事件 ID）
3) 建议核查动作（谁、查什么、看哪张单据）
4) 责任方建议 + 置信度（高/中/低）
AI 的三条红线

不自动扣款：任何金额判定必须人工确认。不自动定责：责任归属涉及商业关系，AI 只给建议。不脱离证据说话：所有结论可点回原始单据，否则视为无效输出。

09 · 实施路线：四期，12–16 周跑通闭环

第 0 期 · 定基（2–3 周）不写代码，但决定成败
  • 料号 / 批次 / 容器 / SN 编码规则定稿并公告，写入合同附件
  • 差异原因字典（D01–D10）与责任判定规则定稿
  • 全量期初盘点：原厂账、IDH 账、实物三方对一次，签字确认基线
  • 选出 1–2 家试点 IDH（配合度高、量大、IT 有基础）

交付物：编码规范 v1.0、差异字典、期初盘点报告、试点协议。验收：三方签字的期初数。

第 1 期 · 三账闭环 MVP（6–8 周）本期核心
  • 主数据、工单下达与接单、发货、收货、领用、库存台账
  • 三账计算引擎 + 差异明细 + 月度对账单（PDF 导出 + 电子签）
  • Excel 模板导入 + 强校验（先走 B 模式，不碰接口）
  • 协同沟通台模式 A + B：工单对话（自动关联工单上下文）+ 差异申辩对话（48h 窗口），消息结构化存储，替代微信群
  • 试点 IDH 真实跑 2 个完整对账周期

验收：账实相符率 ≥ 99%，差异 100% 有原因码，对账周期 ≤ 3 天。

第 2 期 · 生产透明与追溯（6–8 周）
  • 关键工序报工（贴片/测试/老化/包装）、良率、报废、返工
  • 成品 SN 与批次绑定，批次正反向追溯
  • 预警体系：库存安全线、账龄、交期、差异超容差
  • 协同沟通台模式 C：预警处理线程（强制关闭摘要），消息标签（人工/自动），系统事件自动关联消息
  • 头部 IDH 上 PDA 扫码（C 模式）与 ERP 对接（A 模式）

验收：批次追溯 < 30 分钟；报工及时率 ≥ 95%；交期延误可提前 7 天预警。

第 3 期 · AI 与预测协同（8–12 周）
  • 单据 OCR 结构化、差异归因助手、自然语言问数
  • 滚动需求预测 + 安全库存建议 + 产能匹配
  • 对账结果与 ERP 结算、开票、付款联动
  • 沟通智能分析：承诺兑现率追踪、信息断点检测（聊天 vs 事件对照）、争议回溯时间线
  • IDH 绩效画像（交付准时率、质量、配合度）

验收：单据录入工时下降 60%；差异归因人工处理量下降 50%。

范围冻结原则

每一期开始前冻结范围，中途新增需求一律进下一期。这类项目最常见的死法是"顺手把 MES 也做了"——第 1 期一旦扩到工序级管控，交付日期会从 8 周变成 8 个月，且业务方在第 3 个月就失去信心。

10 · 组织与推行机制：技术只占三成

这类平台 70% 的难度在组织，不在代码。IDH 不愿报实数，是理性的——数据就是议价权。所以必须让"配合"的收益大于"隐瞒"的收益。

10.1 合同层面：把数据义务写死

条款写法要点
数据同步义务IDH 须在收货/领用/完工后 X 小时内回传数据；逾期未回传，原厂有权按"发货量扣减已确认消耗"暂估结算
结算依据双方确认：平台锁账对账单为结算唯一依据，邮件/微信/口头约定不作为结算凭证
盘点与核查权原厂有权每季度现场抽盘，差异超容差部分按合同价扣减；连续两次超标触发审计
批次管理禁止自编批次、禁止跨工单挪用；违规导致的追溯失效由 IDH 承担
数据权属与保密数据归原厂与 IDH 共有，平台不得向第三方披露；明确退出时的数据导出方式
系统接入新 IDH 准入前置条件：完成平台接入并通过首期盘点

10.2 给 IDH 的四个"甜头"

  1. 对账自动化：从每月 10 天人工扯皮，变成 3 天系统出单，财务人力直接省下来。
  2. 结算加速：锁账即开票，账期从"对完再算"变成固定 T+3，现金流改善。
  3. VMI / 寄售：芯片放在 IDH 仓库但产权归原厂，IDH 不占资金、不担呆滞，只按实际领用结算。
  4. 自己的经营看板：IDH 能看到自己的良率趋势、批次账龄、交期达成率——这些数据它自己也想要。

C · 未来 30 天可以立刻做的事

  1. 第 1 周：拉一张"料号 × IDH × 批次"的当前账，把三方数字并排放一次。你会发现差异比想象的大，这比任何立项 PPT 都有说服力。
  2. 第 2 周：选 1 家配合度最高的 IDH，做一次 3 天的联合盘点，把差异逐条落原因码。这是编码规则的实战校验。
  3. 第 3 周：定稿编码规范与差异字典（各 2 页纸即可），找法务把"数据同步义务 + 结算依据"两条写进下一次工单合同。
  4. 第 4 周：用 Excel 模板 + 人工对账先模拟跑一个期间，验证流程可行性，再决定系统开发范围。这一步几乎零成本，却能砍掉 30% 的无效需求。
一句话总结

先统编码、再定基线、后建系统、最后上 AI。三账能自动对上，生产透明与消耗可视是自然结果；三账对不上，再多看板也只是把错误的数据展示得更漂亮。

本文档为方案设计建议，具体功能边界、投入与排期需结合 IDH 数量、年出货量、现有 ERP 状况、结算模式（购销 / 委外 / 寄售）做裁剪。建议在立项评审前完成一次"现状三账并表"与"试点 IDH 走访"，用真实差异数据校准范围。
