# IDH 协同平台 · 系统架构设计文档

> 版本: V1.0 | 日期: 2026-11 | 基于《IDH协同平台建设方案》

---

## 1. 概述

### 1.1 系统定位

IDH 协同平台是面向芯片原厂与多家 IDH（方案商）的**供应链协同对账系统**。核心目标不是"监控 IDH"，而是建立**工单账、库存账、消耗账三账对齐**的共同基准，使差异可定位、进度可承诺、结算可依据。

### 1.2 核心设计原则

| # | 原则 | 架构含义 |
|---|------|---------|
| 1 | 一个料号、一个批次、一个基准单位 | 主数据唯一源（原厂 ERP），向下同步 |
| 2 | 事件驱动、只追加、不可篡改 | 采用 Event Sourcing，账由事件累加算出 |
| 3 | 双向透明不是单向监控 | IDH 同样看到原厂的订单池/配额/在途/结算进度 |
| 4 | 最小采集 | 只采对账和交期必需的节点（4-5 个工序），不做全工序 MES |
| 5 | AI 只做辅助、结论可溯源 | AI 输出必须引用事件 ID 或单据号 |

### 1.3 系统边界

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  原厂 ERP    │────▶│  IDH 协同平台 │◀────│  IDH ERP     │
│  (SAP/Oracle)│     │              │     │  (金蝶/用友)  │
```

### 2.1 各层职责与依赖规则

| 层 | 职责 | 依赖方向 |
|----|------|---------|
| 渠道与接入 | 多终端适配、认证拦截、请求路由 | → 协同应用层 |
| 协同应用 | 业务页面、看板、对话、AI 交互 | → 核心业务域 |
| 核心业务域 | 领域模型、业务规则、状态机 | → 数据与规则层 |
| 数据与规则 | 事件存储、三账计算、差异归因、指标聚合 | → 基础支撑层 |
| 集成层 | 外部系统对接、消息队列、OCR | ← 可被各层调用 |
| 基础支撑 | 认证、权限、审计、消息推送、部署 | 被所有层依赖 |

**硬规则：上层可依赖下层，下层不可依赖上层。跨层依赖仅允许对基础支撑层。**

## 4. 技术栈总览

| 层次 | 选型 | 版本 | 理由 |
|------|------|------|------|
| **前端 (PC)** | Vue 3 + TypeScript + Vite | Vue 3.4+ | 内网系统，无需 SSR；生态成熟 |
| **移动端** | H5 (Vant UI) | Vant 4 | 车间扫码不装 App，浏览器即用 |
| **后端** | Java 17 + Spring Boot 3 | Spring Boot 3.2+ | 事务/并发控制成熟，适合单据类系统 |
| **备选后端** | Python 3.12 + FastAPI | — | 团队熟悉 Python 时可用 |
| **主数据库** | PostgreSQL | 15+ | RLS 租户隔离、JSONB 存事件、递归 CTE 做批次追溯 |
| **缓存** | Redis | 7+ | 会话、三账快照缓存、分布式锁 |
| **消息队列** | Apache Kafka | 3.6+ | 事件总线天然支持"只追加"与事件重放 |
| **分析库** | Apache Doris 或 ClickHouse | — | 对账聚合查询与看板，避免压主库 |
| **对象存储** | MinIO | — | 单据影像、盘点照片、签收单，S3 兼容 |
| **AI 推理** | vLLM + Qwen2.5-32B-Instruct | — | **必须私有化**；价格/产能/良率不许走公有云 |
| **嵌入模型** | bge-m3 + pgvector | — | 向量检索历史相似案例 |
| **OCR** | PaddleOCR | — | 私有化 OCR，CPU 即可 |
| **容器编排** | Docker Compose (首期) / K8s (规模) | — | 首期 MVP 规模小，Compose 够用 |
| **认证** | JWT + 企业内部 SSO 对接 | — | 无状态认证，支持 LDAP/OIDC |
| **消息推送** | 企微 Webhook / 邮件 SMTP | — | 分级预警推送 |

## 5. 非功能性需求

### 5.1 安全性

| 需求 | 实现方式 |
|------|---------|
| **租户数据隔离** | PostgreSQL RLS + `tenant_id` 强制过滤，禁止仅在应用层做 `WHERE` |
| **字段级脱敏** | `unit_price` 对非本家 IDH 返回 NULL；`customer_id` IDH 侧脱敏 |
| **认证** | JWT Short-lived (15min) + Refresh Token (24h)；支持 SSO |
| **传输加密** | TLS 1.3 全链路 |
| **审计** | `event_log` 记录所有业务操作，不可篡改 |
| **AI 数据安全** | 私有化部署，数据不出内网。**禁止**走公有云 API |

### 5.2 性能

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 页面首屏加载 | < 2s | PC 端内网 |
| 扫码响应 | < 500ms | 车间 H5/PDA |
| 三账日核对 | < 5min | 凌晨 02:00 全量重算 |
| 对账单生成 | < 30s | 含差异明细 |
| API 响应 (P95) | < 500ms | 读操作；写操作 < 1s |
| 并发写入 | 500 TPS | 扫码高峰，Kafka 削峰 |

### 5.3 可用性

| 指标 | 目标 |
|------|------|
| 系统可用率 | ≥ 99.5%（允许月末对账窗口期计划维护） |
| RTO | < 4 小时 |
| RPO | < 1 小时（WAL 归档持续同步） |
| 优雅降级 | 分析库不可用时对账查询回退到主库（限流） |

### 5.4 可扩展性

| 维度 | 策略 |
|------|------|
| **水平扩展** | 后端无状态，K8s HPA 按 CPU/请求量伸缩 |
| **读写分离** | 对账/看板读操作走分析库，写操作走主库 |
| **IDH 接入扩展** | Excel（B 模式）→ H5/PDA（C 模式）→ API（A 模式）渐进式对接 |

## 6. 关键架构决策记录 (ADR)

### ADR-001: 事件溯源（Event Sourcing）

**决策:** 所有业务状态变更以不可变事件写入 `event_log`，账由事件累加计算。

**理由:**
- 审计要求：任何时候可以回溯谁在什么时间做了什么
- 三账需要多时间点可追溯，简单 CRUD 无法满足
- 差异归因需要完整的事件时序

**代价:** 查询当前状态需要聚合事件，增加复杂度。用**双轨策略**缓解：事件到达时增量更新快照（看板用），每日凌晨全量重算（对账用）。二者不一致即报警。

### ADR-002: 双轨计算

**决策:** 三账计算结果同时存在于增量快照和全量重算结果中。

**理由:** 增量可能因异常丢事件而漏算；全量重算作为每日基准。两个结果不一致时自动报警，防止"静默丢账"。

### ADR-003: 数量账与金额账分离

**决策:** `wo_line` 的四个数量字段只参与数量勾稽，`unit_price` 只参与金额结算，两者不同步更新。

**理由:** 避免"A 账按发票扣、B 账按领料扣"的经典设计错误。统一以"领用事件"为消耗确认口径。

### ADR-004: 私有化 AI 部署

**决策:** AI 推理全部走私有化 vLLM 服务，不走公有云 API。

**理由:** 价格、产能、良率是核心商业机密，不可发往外部。32B 级模型在 2×L20 上可运行，成本可接受。

### ADR-005: PostgreSQL RLS 作为租户隔离的唯一兜底

**决策:** 租户数据隔离的**最后防线**在数据库 RLS，不在应用层 `WHERE`。

**理由:** 应用层过滤漏写一处就是数据泄露。RLS 确保即使应用 bug 也不会跨租户返回数据。

## 8. 异常处理策略

### 8.1 事件丢失 / 消息队列故障

- Kafka 消费者 offset 手动提交，确保至少一次处理
- 每日凌晨全量重算作为兜底，覆盖增量遗漏
- 双轨结果不一致 → 自动报警 → 人工介入

### 8.2 数据库故障

- 主库故障 → 从库自动提升（Patroni + etcd）
- 分析库故障 → 对账查询降级到主库（限流保护）

### 8.3 外部系统不可用

- 原厂 ERP 不可用 → 工单/发货单可人工填写，ERP 恢复后同步
- IDH 侧网络不通 → Excel 离线模板填写，恢复后批量导入
